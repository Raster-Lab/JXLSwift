# v0.9.0 — Pixel Accuracy Investigation

Captures the state of the textured-fixture pixel-byte-equality work
that's the headline goal of v0.9.0. As of writing, decoder produces
correct DC values + correct strategy + IDCT pipeline pixel patterns
but with O(15-100) per-channel byte drift on textured cjxl-d=0.5...10
fixtures vs `djxl 0.11.2`.

## Critical localisation (v0.9.0e + v0.9.0f diagnostics)

### v0.9.0f: gradient diagnostic narrows further

`testVarDCT_GradientBlock_DjxlByteDiff` decodes 8×8 cjxl-d=1 single-
axis gradient blocks (R varies, GB constant 128) and compares per-
pixel to djxl. Result on horizontal R = 100 + x·16 ramp:

| Test variant | Pixel 0 R | Implied AC mag | Correct AC mag |
|---|---|---|---|
| Current (`×64`) | 156 (= DC mean) | 0 | 56 |
| `×64` removed | 84 (overshoot) | 72 | 56 |
| djxl | 100 | 56 | — |

**Two hard data points:**

1. With `scaledForBitstream(×64)` applied (current main), the AC
   contribution is **zero** — output is purely the DC block mean.
2. With `×64` dropped, the AC contribution emerges at ~72 (linear
   ramp residual). Correct value is 56.

The ratio 72/56 ≈ 1.286 isn't an obvious clean factor. It hints
that the actual fix isn't just "remove ×64" — there's a second
scaling discrepancy. Possibilities:

- A different seed normalisation (e.g., per-num-bands divisor).
- Channel mapping mismatch (our X/Y/B label order vs libjxl's
  internal ordering for the `DCT()` defaults).
- A missing per-axis or per-rank multiplier in `getQuantWeights`.
- An IDCT-side scaling (e.g., libjxl's `DCTSlow` vs our libjxl-
  ported `LibjxlIDCT` differ on a non-DC normalisation factor).



`testVarDCT_UniformBlock_DjxlByteDiff` decodes 3 cjxl-d=1 uniform-
colour 8×8 blocks (red, grey, blue-tinted) and compares per-pixel
to djxl. **Result: ±1 byte per channel, every sample.**

Uniform-colour input produces near-zero AC coefficients (only DC
carries signal), so this test exercises:

- DC dequant (`mulDC[c] * dcExtraFactor`)
- DC-CFL (`X' = X + dcCflX·Y`, `B' = B + dcCflB·Y`)
- OpsinXYB inverse + sRGB OETF + uint8 round

…all within ±1 byte. **The DC + OpsinXYB pipeline is correct.**
The O(15-100) byte drift on textured cjxl-d=0.5..10 SWEEP fixtures
is therefore entirely localised to the **AC contribution**:

- AC entropy decode (zigzag scan, ANS context routing)
- AC dequant (`AdjustQuantBias` + per-coef weight + invQuantAC)
- AC-CFL (per-tile slope multiplier)
- IDCT (verified byte-equal in isolation, but pipeline scaling could
  still divert at the dequant→IDCT bridge)

| **Per-cell QF stamping** | Multi-block first-block QFs stamped onto all covered cells (v0.8.0j). Indexed correctly. |
| **AC `prev` flag** | `prev = u != 0` (v0.8.0k fix). Was inverted. Now matches libjxl. |
| **Channel iteration order** | `{1, 0, 2}` storage order (X, Y, B). Was a latent Y/X swap. Fixed in v0.8.0e. |

## Open suspects

### Quant matrix scaling (`scaledForBitstream(×64)`)

**The strongest suspect.** Per libjxl `DecodeDctParams`, the seed
`distance_bands[c][0] *= 64.0f` is applied ONLY when params are
decoded from the bitstream (DCT mode). For LIBRARY mode (1-bit
`all_default` flag set, which is the case for all our test fixtures),
NO `×64` is applied.

Empirical experiments:
- **WITH `×64` (current main)**: our weights are 64× larger than
  libjxl's. Dequant values 64× smaller. Pixel output is DC-dominated
  (small AC variation). Channel means biased high (8×8: +19/+7/+10
  vs djxl).
- **WITHOUT `×64`**: weights match libjxl. Pixel output spans full
  dynamic range. Some channel means improve dramatically (16×16
  within ±3 of djxl, 32×32 within ±2). BUT per-pixel SWEEP byte-
  diffs WORSEN due to saturation/color drift (max R=117, mean 15+).

The conflict suggests the actual bug isn't pure ×64 vs not — it's
something else that interacts with the quant scaling. Possible:

1. **`intensity_target`-driven matrix scaling** (libjxl `opsin_params.cc:42`
   `inverse[j][i] * (255.0f / intensity_target)`) — for default
   `intensity_target = 255` this is 1.0 (no effect), but worth
   double-checking if the bitstream sets a different target.
2. **`x_dm_multiplier` / `b_dm_multiplier`** (already applied per
   v0.8.0 commit `92f58fc`) — verify it's the right factor for this
   fixture. Default `qm_scale = 3` gives `0.8` multiplier.
3. **Per-block AC dequant biases** (libjxl `AdjustQuantBias` — adds a
   small constant before multiplying by the dequant matrix). NOT
   currently in our code; likely a small correction.
4. **The `mul` parameter in `DequantDC`** (= `1.0f / (1 << extra_precision)`).
   Already applied as `dcExtraFactor` in our code.

### ~~`AdjustQuantBias`~~ — implemented in v0.9.0d (eliminated as suspect)

libjxl's per-block AC dequant has a `quantized_x_int = AdjustQuantBias(...)` step
that biases the quantised int before multiplying by `dequant_matrix`:

- `q == 0 → 0`
- `|q| == 1 → ±zeroBias[c]` (default `0.5`)
- `|q| >= 2 → q − biasNumerator / q` (default `0.145`)

Implemented in v0.9.0d (`Sources/JXLSwift/VarDCT/AdjustQuantBias.swift`)
and wired into all 7 AC dequant call sites (DCT8/16/32/64 + DCT8x16,
DCT16x32, DCT32x64). **Net pixel impact is essentially neutral**:
SWEEP byte-diff means moved by ±0.03 per channel (some fixtures
slightly up, some slightly down). Max byte-diffs unchanged. Confirms
the `AdjustQuantBias` correction is too small to be the dominant bug
on textured cjxl-d=0.5..10 fixtures.

### libjxl encoder writes vs our decoder reads

Worth verifying: maybe the libjxl ENCODER applies a per-coefficient
transform we're not reversing. Encoder logs would help.

## v0.9.0g experiments (additional eliminations)

Three further experiments performed on the gradient fixture, all
reverted; findings preserved here for the next investigator.

### X / Y band swap (disproven)

Swapped which `qweights` row is used for the X channel data vs the
Y channel data. Result: catastrophic regression — `[GRAD horiz]
max=(R=209)`, `[BYTE-DIFF d=0.5] max=(R=238)`. Channel mapping
`(X=0, Y=1, B=2)` to band-row `(x=3150 seed, y=560 seed, b=512 seed)`
is correct.

### Y dequant scaling probe

With `×64` removed and `Y dequant *= F`:

| F | Pixel 0 R | Notes |
|---|---|---|
| 1.0 | 84 | Baseline (no Y mul) |
| 0.8 | 88 | Slight improvement, AC contribution -5.5 % |
| 0.5 | 94 | Better, but still 6 below djxl=100 |
| target ≈ 100 | (would need F ≈ 0.3) | Y-only mul cannot fully close the gap |

Conclusion: the gap isn't a clean per-channel multiplier on Y. The
residual signal must be in the X or B AC contribution as well, or
in a structural difference (e.g., dequant→IDCT bridge or
`getQuantWeights` interpolation formula).

### v0.9.0h: per-block AC integer trace

`JXL_TRACE_AC=1 swift test --filter testVarDCT_GradientBlock_DjxlByteDiff`
prints the first 8 quantised AC integers per channel for the first
block of every fixture. Sample output for the horizontal R-ramp
(R = 100 + x·16, GB = 128 constant), cjxl-d=1:

```
TRACE_AC blk0 c=0 (X) first8=[0,-17,1,-2,0,0,0,0]
TRACE_AC blk0 c=1 (Y) first8=[0,-7,0,0,0,0,0,0]
TRACE_AC blk0 c=2 (B) first8=[0,0,0,0,0,0,0,0]
TRACE_AC blk0 dc=(648, 38, -1) qf=10 globalScale=5111
```

Observation: |X AC[0,1]| = 17, |Y AC[0,1]| = 7, |B AC[0,1]| = 0.
For an R-only gradient, expected sensitivity ratio would put |Y|
> |X| > |B|; quantizer weighting (X seed 3150 vs Y seed 560) would
flip the relative integer magnitudes to roughly |Y|/|X| ~ 1.3.
Observed ratio is |X|/|Y| = 2.4 — anti-correlated with first-order
analysis. Either the analytical sensitivity calculation is too
coarse (likely — it ignores the quantizer's perceptual model) or
the encoder's per-channel weighting is structurally different from
what we model.

A definitive check requires a cjxl decode trace (instrumented libjxl)
of this exact 8×8 fixture so we can compare per-coefficient quantised
integers byte-for-byte.

#### Forward-direction sanity check on DC

Computing first-principles forward OpsinXYB on the gradient mean
(`R_mean = 156, G = B = 128`, sRGB→linear via standard OETF):

| Channel | Predicted DC (forward) | Observed DC dequant | Ratio |
|---|---|---|---|
| Y | ~0.444 | 0.477 | ~1.07 |
| B | ~0.444 | 0.476 | ~1.07 |
| X | depends on per-pixel L vs M asymmetry | +0.00350 | within plausible range |

Y and B match within ~7 % of the analytical estimate; small enough
to be sRGB-OETF-conversion imprecision in the analytical calc. X is
small-magnitude and dominated by per-pixel L-vs-M asymmetry under
the cube-root nonlinearity (`mean(cbrt(L)) - mean(cbrt(M))` does
not equal `cbrt(mean(L)) - cbrt(mean(M))`), so a closed-form sign
prediction isn't reliable. The DC pipeline is consistent with the
forward XYB transform; the residual ~7 % gap on Y/B is a candidate
for "what makes pixel 0 R land at 84 instead of 100 when ×64 is
dropped" — small per-channel scaling errors compound through the
inverse OpsinXYB.

### v0.9.0k: libjxl source comparison + Phase R bypass

Cloned libjxl 0.11.2 source locally and compared the decode chain
against ours line by line. Findings:

**Confirmed identical formula:**
- `dequant_matrix[k] = 1 / weight[k]` storage layout (libjxl
  `quant_weights.cc::ComputeQuantTable` line 330-332).
- Per-coefficient dequant: `dequant_x = AdjustQuantBias(quantized_x_int)
  * dequant_matrix[k] * (inv_global_scale / quant) * x_dm_multiplier`
  (libjxl `dec_group.cc::DequantLane` line 105-130). Y has no extra
  multiplier; X gets `x_dm_multiplier`; B gets `b_dm_multiplier`.
- `LIBRARY` defaults are NOT pre-multiplied by 64 (verified by exhaustive
  grep — `*= 64` appears only once in all of libjxl, in `DecodeDctParams`
  for the bitstream-decoded DCT-mode path).
- IDCT scale and matrix construction (libjxl `dct_for_test.h::IDCT1D`
  vs our `LibjxlIDCT.idct1D`).
- Loop filter constants and Gaborish kernel.

**Confirmed via runtime trace:**
- Our `qweights[Y, 0, 1] = 560` matches libjxl's expected weight
  (when `×64` is dropped).
- Our dequant Y AC[0,1] = -0.01598 matches libjxl's expected
  `AdjustQuantBias(-7) * (1/560) * 1.282 = -0.01598`.
- LoopFilter for cjxl-d=1 fixtures: `gab=true gabCustom=false
  epfIters=1 epfSharpCustom=false epfWeightCustom=false
  epfSigmaCustom=false`. All custom-flag-false → default weights only.
- xQmScale=3 (mul=0.8), bQmScale=2 (mul=1.0). Defaults.

**Behavior with `×64` dropped:**
- Gradient pixel 0 R = 84 (target djxl=100). With Phase R bypassed
  (`JXL_SKIP_PHASE_R=1`): pixel 0 R = 80. So Gaborish/EPF accounts
  for ~4 of the 16-byte gap; the remaining 12 is upstream.
- SWEEP regresses (max R goes from 26 → 109 on d=0.5).

**Conclusion:** The dequant formula is correct, the IDCT matches
libjxl structurally, and the post-IDCT pipeline matches the spec.
Yet there's a residual ~12-byte / 30-byte (depending on signal) gap
in the IDCT pixel output that doesn't match djxl. Closing it requires
running an *instrumented* libjxl side-by-side to compare the
intermediate `block[]` values right after `LowestFrequenciesFromDC`
returns — which is the entry to the IDCT call in libjxl's render
pipeline. The handoff note in
[NEXT-STEP-libjxl-trace.md](NEXT-STEP-libjxl-trace.md) captures the
specific probe points needed.

**Diagnostic infrastructure shipped:**
- `JXL_TRACE_AC=1` — dumps quantised AC ints + dequantised float
  values + qweights + scale factors + loop-filter custom flags.
- `JXL_SKIP_PHASE_R=1` — bypasses Gaborish + EPF to isolate raw
  IDCT pixel output.

### v0.9.0l: PARTIAL ROOT CAUSE — libjxl coefficient layout is transposed

**The claim and its limit.** The transposed-coefficient theory holds
mathematically: libjxl's `ComputeScaledDCT(P) = M·P^T·M^T` for ROWS≥COLS
strategies (verified by source-trace through `dct-inl.h`), so the
bitstream stores `vanilla(P^T)` for square strategies. Combined with
dropping the LIBRARY-mode `×64` (which is bitstream-decode-only,
verified by exhaustive grep of libjxl source), this should give
byte-equality.

**The empirical surprise.** Applying `drop ×64 + transpose` improves
the gradient fixture dramatically:

| Test (DCT8x8 fix only) | Before | After |
|---|---|---|
| GRAD horiz max R | 58 | **17** |
| GRAD horiz mean R | 32.19 | **3.69** |

But applying it across all square strategies REGRESSES the SWEEP
textured fixture across all distances. With `×64` re-applied AND
the transpose, SWEEP also regresses. The two changes interact in
a way the simple transposed-layout theory doesn't predict.

**What's still missing.** The encoder's actual quantisation step
(libjxl `enc_group.cc::QuantizeBlockAC`) uses `qm = InvDequantMatrix`
(= `weight`, not `1/weight`) multiplied by `Scale * quant * qm_multiplier`.
A first-principles analytical estimate gives quantised integers ~3.4×
larger than what cjxl actually emits in the bitstream — confirming
*some* additional scaling we haven't located. Possible candidates:

1. The encoder applying a `1/64` factor in EncodeDctParams when
   serialising DCT-mode params, paired with the decoder's `×64` —
   meaning library-default tables conceptually live in the
   "scaled-up" form, even though the constants themselves don't
   show ×64. Need to check if the LIBRARY constants ARE the
   scaled-up form.
2. A perceptual / butteraugli-driven adjustment in the encoder that
   isn't part of the simple round-trip formula.
3. A different path through `ComputeQuantTable` for LIBRARY mode
   that we haven't traced.

**Status.** Reverted the partial fix; baseline tests still pass with
0 failures. The mathematical insight (libjxl coefficient layout is
transposed for ROWS≥COLS) is preserved in this doc and in the
`transposeSquareInPlace` helper (kept dormant in `JXLDecoder`) for
future use once the second factor is identified.



**Hypothesis confirmed by source inspection + numerical verification.**

#### The bug (matrix form)

libjxl's `ComputeScaledDCT` (encoder) computes:

    C = M · P^T · M^T = vanilla_DCT(P^T)

where `M` is the 1-D DCT matrix and `P` is the input pixel block.

So **the bitstream coefficient block is in TRANSPOSED layout** relative
to the standard "block[y, x] = vanilla DCT[k_y, k_x]" convention.

libjxl's decoder uses `ComputeScaledIDCT(C) = M · C^T · M^T = vanilla_IDCT(C^T)`,
which correctly inverts the encoder.

Our decoder applied vanilla 2-D IDCT directly to `C` (which would
give P^T, the transposed pixel block). Effectively, **we were decoding
the transposed image** for any block with non-zero AC — but the
×64 quant matrix scaling was making AC magnitudes ~64× too small,
so the visual error was masked into a "DC-dominated" output.

#### Confirmation via row0/col0 trace

For an 8×8 horizontal R-ramp (cjxl-d=1), the AC content should be at
*horizontal-frequency* positions in vanilla DCT. With the trace dumping
both first row (flat 0..7) and first column (flat 0, 8, 16, ...) of
the bitstream-decoded `acBlocks[0][c]`:

```
TRACE_AC blk0 c=0 (X) row0=[0,0,0,0,0,0,0,0]
                      col0=[0,-17,1,-2,0,0,0,0]
TRACE_AC blk0 c=1 (Y) row0=[0,0,0,0,0,0,0,0]
                      col0=[0,-7,0,0,0,0,0,0]
```

**Row 0 is all zeros; the AC content is in col 0** (flat positions 8,
16, 24). That confirms libjxl's TRANSPOSED layout — the encoder put
horizontal-frequency content at the column-0 flat positions, which in
transposed convention map to vanilla `[k_x, 0]` = horizontal AC at
frequency `k_x`.

#### Two-part fix

1. **Drop `scaledForBitstream(×64)`** for LIBRARY-mode quant matrix
   defaults (verified against libjxl source — `*= 64` only applies on
   the bitstream-decoded DCT-mode params path).
2. **Transpose the dequantised coefficient block** before our
   vanilla IDCT (since we use vanilla `M · X · M^T` and the bitstream
   `X` is in transposed convention).

#### v0.9.0l measured impact (DCT8x8 only)

| Test | Before fix | After fix |
|---|---|---|
| GRAD horiz max R | 58 | **17** |
| GRAD horiz mean R | 32.19 | **3.69** |
| GRAD diag max R | 57 | **15** |

Gradient byte-diff on R channel **improves 3.4× on max, 8.7× on mean.**

Pixel 0 R is invariant under the transpose (M[0, i] · M[0, j] is
symmetric in i, j) so it remains at 84 vs target djxl 100. Other
pixels improve dramatically. The residual ~16-byte gap on pixel 0 is
likely Gaborish + EPF + OpsinXYB precision interplay.

**SWEEP regresses on d=0.5/1.0/2.0 fixtures** because they use multiple
strategies (DCT16x16, DCT32x32, asymmetric variants) that haven't
been fixed yet. v0.9.0m will extend the fix to all strategies. d=5,
d=10 are unchanged (low-AC content; the fix has no effect when AC
magnitudes are already near-zero).

### What's still to try

- **Linear vs geometric interpolation** in `QuantWeights.interpolate`.
  We use geometric (`a * (b/a)^frac`); verify libjxl uses the
  same. Differences only matter where adjacent curve entries differ.
- **Per-block-size normalisation** in `getQuantWeights`. Possibly
  a `kAcStrategyMul` factor we haven't ported.
- **Exponentiation in weight computation**. libjxl might compute
  `weight = exp(interpolated_val)` instead of using the value
  directly.
- **Hand-decode a libjxl reference** for one fixture to compare
  intermediate AC dequant values directly.

## Suggested next bites

Now that the bug is localised to AC contribution:

1. ~~Implement `AdjustQuantBias`~~ — done in v0.9.0d, neutral.
2. ~~Build a uniform-colour diagnostic test~~ — done in v0.9.0e,
   localised the bug to AC.
3. Build a "single-tone gradient" fixture (e.g., horizontal-only
   8×8 ramp in R only). This exercises ONE non-zero AC coefficient
   at a known frequency. Compare to djxl per-pixel — if matched,
   the bug is in higher-frequency AC; if not, it's in low-freq AC.
4. Verify acBlocks decoded values vs djxl: dump our `acBlocks[0]`
   (Int32 quantised AC) for a SWEEP fixture and compare against
   what djxl decodes from the same bitstream. If they match, the
   bug is post-decode (dequant/IDCT bridge). If they differ, the
   bug is in the AC entropy decoder.
5. Audit the dequant→IDCT bridge: libjxl's IDCT has a specific
   normalisation convention (`DC = mean`), and our `LibjxlIDCT` /
   `AccelerateDCT` were validated against synthetic coefficient
   inputs but NOT against actual dequantised values from a real
   fixture. A hidden bridge factor (e.g., per-axis `scales` table
   missing from non-LLF positions) would only show up under real
   data.
6. Check ZigZag scan-order off-by-one — `naturalCoeffOrderDCT8`
   was verified as a permutation of 0..63, so this is unlikely
   but should be explicitly tested via a hand-crafted bitstream.
