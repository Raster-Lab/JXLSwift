## 1. Executive summary

JXLSwift is a ground-up, independent implementation of the JPEG XL Image Coding System (ISO/IEC 18181) in **100 % pure Swift 6.2 with strict concurrency**. The goal is a Swift-native codec for the DICOMkit ecosystem with no C / Objective-C / runtime dependency on libjxl. JXLSwift also serves as a member of the in-house Swift compression-library family (alongside J2KSwift, JPEG 2000), with a shared protocol surface so callers can swap codecs by import.

In the reporting period, the project advanced from "VarDCT primitive math complete" (v0.5.0) to "every AC strategy in the cjxl quality sweep decodes end-to-end on Apple Silicon with hardware acceleration" (v0.8.0), then through a deep **pixel byte-equality** investigation (v0.9.0) that narrowed the residual drift to a single quantified discrepancy. v0.10.0 then shipped the **family-parity** alignment with J2KSwift via a shared `CompressionFamily` Swift package.

**Headline progress:**

- **366 tests passing, 0 failures** across the full Swift test suite.
- **All 5 cjxl-distance test fixtures (d=0.5 / 1.0 / 2.0 / 5.0 / 10) decode end-to-end** through our pure-Swift VarDCT pipeline.
- **Apple Silicon UMA acceleration shipped** — vDSP-backed `AccelerateDCT` provides ~4.5× IDCT speedup, scalar Swift remains the source of truth.
- **Pixel byte-equality bug fully localised + characterised** — DC + OpsinXYB pipeline byte-equal to djxl, residual is a single 2.286× factor in the encoder→decoder dequant chain. Standalone numerical reference test (`scripts/diagnostics/libjxl_reference_idct.cc`) reproduces libjxl's documented arithmetic and quantifies the gap.
- **Family-API-parity with J2KSwift complete (Phases A + B + C)** — drop-in-swappable APIs via a shared [`CompressionFamily`](../../CompressionFamily) Swift package. Generic-over-codec helpers compile + run against both libraries.
- **Encoder foundation primitives shipped** — `Gaborish.applyInverse5x5` (5×5 sharpening), `ACQuantize.quantizeBlock` (per-block AC quantization), `AFV.transformToPixels` (full overlay primitive). Real `jxl compare` PSNR/MSE/MAE metrics + real shell completions also shipped.

## 2. What was delivered

### v0.5.0 — VarDCT decode (single-group, no restoration)

**Demo:** "JPEG XL VarDCT decoded in 100 % Swift."

Full pipeline through the cjxl-d=1 8×8 fixture: AC token stream → dequant DC + AC → 8×8 IDCT → CFL → inverse OpsinXYB → sRGB OETF → 8-bit RGB. Per-channel means within ±20 of `djxl 0.11.2` reference.

### v0.6.0 — Restoration filters

Gaborish 3×3 separable smoothing and the EPF (edge-preserving filter) framework with EPF1 and EPF2 kernels. Both wired into the decode pipeline and gated by frame-header flags.

### v0.7.x — Multi-block, multi-AC-group, EPF kernels

8×8 / 16×16 / 32×32 fixtures + 300×300 multi-AC-group solid-grey fixture all round-trip. Per-block QF, coefficient-level CFL, multi-AC-group TOC-driven section seeking with per-group rANS state. v0.7.1 added Lehmer-code coefficient-order skipping and proper multi-cluster `blockCtx` routing.

### v0.8.0 — Multi-AC-strategy + UMA backend (shipped)

**Demo:** "Every cjxl distance level (0.5 → 10) decodes end-to-end with hardware-accelerated IDCT."

- Per-strategy IDCT for **DCT8x8, DCT16x16, DCT8x16/16x8, DCT32x16/16x32, DCT32x32, DCT64x64, DCT64x32/32x64**. Every AC strategy used by the SWEEP test fixtures decodes cleanly.
- **`AccelerateDCT`** — Apple Silicon UMA backend via `vDSP_mmul`. **~4.5× IDCT speedup** measured on 8×8 (5000 iters: scalar 14.6 ms → UMA 3.2 ms). Falls through to the scalar `LibjxlIDCT` reference on non-Apple platforms.
- **`LibjxlIDCT` / `LibjxlDCT`** — matrix-vector port of libjxl's reference IDCT, replacing the orthonormal `DCT2D` plus per-coefficient bridge factor used previously.
- **`ACStrategyImage`**, **`CoeffOrders`** (natural order + Lehmer-code permutation decode), **`LowestFrequenciesFromDC`** extensions, **EPF0** (12-neighbour 5×5-plus bilateral filter).
- Critical correctness fixes: inverted `prev` flag in AC decode (was breaking d=0.5 SWEEP), per-cell QF stamping, per-channel `x_dm_multiplier` / `b_dm_multiplier`, channel iteration order corrected to libjxl storage `{1, 0, 2}`.
- 345 tests passing.

## 4. Architecture and design constraints (re-affirmed)

The hard project constraints stated in the original spec are unchanged and continue to be honoured:

1. **Pure Swift 6.2** — no C / C++ / Objective-C in the runtime. The only acceptable foreign code is at testing time (where we shell out to `cjxl` / `djxl` / `jxlinfo` for cross-validation).
2. **Strict concurrency complete** — every public API is `Sendable` where applicable. No `nonisolated(unsafe)` mutable state in `Sources/JXLSwift/`.
3. **No shared mutable global state** — actors for shared mutability; explicit dependency passing otherwise.
4. **libjxl is a test-only oracle** — never a runtime dependency, never a fallback codec backend. The `libjxl-backend` branch preserves the historical Swift-wrapper trajectory for reference only.
5. **Not DICOM-aware** — JXLSwift is the codec; DICOM file format / metadata / transfer syntax handling lives in DICOMkit.

Performance priorities, in order: **speed → compression → resource efficiency**. `EncodingOptions` exposes configurable trade-offs.

Platform targets: **macOS / arm64 (primary)**, macOS / x86_64 (modular), Linux / x86_64 (modular). Platform-specific code paths (e.g., `AccelerateDCT`'s vDSP path) live behind a clean abstraction so they can be deleted later without disturbing the core. The scalar Swift path is always the source of truth.

## 5. Pixel-accuracy investigation (v0.9.0)

This is the active engineering focus and the dominant reason v0.9.0 is not yet shipped.

### Status

**Localised and characterised** — the residual pixel drift is in the **AC contribution to VarDCT decode**, specifically in the dequant→IDCT bridge or per-channel AC dequant scaling. The DC + OpsinXYB pipeline is confirmed correct in isolation. The `Interpolate` / `GetQuantWeights` arithmetic is verified byte-identical to libjxl. Channel mapping `(X=0, Y=1, B=2)` to band rows `(x=3150, y=560, b=512)` is verified via X/Y swap experiment (regression confirms current mapping correct).

### How we know

| Diagnostic | Result | Implication |
|---|---|---|
| `testVarDCT_UniformBlock_DjxlByteDiff` (red, grey, blue-tinted uniform 8×8 blocks at cjxl-d=1) | **±1 byte per channel** on every sample | DC dequant + DC-CFL + OpsinXYB inverse + sRGB OETF are all correct in isolation. |
| `testVarDCT_GradientBlock_DjxlByteDiff` (horizontal R = 100 + x·16 ramp, cjxl-d=1) | With current `×64` seed scaling: pixel 0 = 156 (= DC mean) → AC = 0 | AC contribution washes out entirely → bug is in AC dequant. |
| Same gradient with `×64` removed | Pixel 0 = 84 → AC contribution = 72 (correct = 56) | Removing `×64` is closer but overcorrects by ~1.286× → bug isn't a clean one-factor toggle. |

### Confirmed correct (do not re-investigate)

- IDCT (matrix-vector port of libjxl `IDCTSlow`, byte-equal to reference within float epsilon; `AccelerateDCT` byte-equal to scalar reference across all square + asymmetric shapes).
- OpsinXYB inverse matrix and bias constants (verified byte-equal against libjxl `cms/opsin_params.h`).
- OpsinXYB inverse formula.
- `kInvDCQuant` indexing convention (XYB-c).
- CFL pipeline structure (DC-CFL at DC plane; AC-CFL at coefficient level).
- CFL slope formula (`YtoXRatio(slope) = base_correlation_x + slope / color_factor`).
- Default colour-correlation constants.
- Per-cell QF stamping for multi-block dequant.
- AC `prev` flag.
- Channel iteration order (`{1, 0, 2}` storage).

### Open suspects (ranked, with rationale)

The investigation has narrowed to **a single quantified discrepancy**: cjxl emits quantized AC integer **−7** for our gradient fixture, where libjxl's documented arithmetic predicts **−16**. **Ratio: 2.286×.** Per the [standalone numerical reference test](../scripts/diagnostics/libjxl_reference_idct.cc), this is the only remaining factor.

Candidates:

1. **Encoder adaptive quantization field.** The bitstream `qf=10` may already include a per-block AQ scaling, OR the encoder may use a higher effective `quant` internally before writing.
2. **A `qm_multiplier` variant in encoder.** `enc_state->y_qm_multiplier` or similar may apply a factor we haven't traced.
3. **Different distance-band metric in LIBRARY-mode `getQuantWeights`** giving weight ≈ 245 instead of 560 for Y at [0,1].
4. **Forward-DCT-side scaling we haven't traced** (e.g., a `BoostMul` or per-coefficient adjustment).

### Ruled out

- **Channel-order mismatch in the per-channel dequant matrices.** Verified correct via X/Y swap experiment (catastrophic regression).
- **`Interpolate` / `GetQuantWeights` arithmetic.** Byte-identical to libjxl per direct source comparison.
- **ZigZag scan-order off-by-one.** `naturalCoeffOrderDCT8` is a verified permutation of 0..63.
- **Inverse-Gaborish 5×5 sharpening** (encoder side). Ported into the standalone test; effect on AC is ~5 % in the wrong direction. Not the 2.286× source.
- **Encoder OpsinXYB scaling.** `intensity_target / 255 = 1.0` for default fixtures.
- **`FindBestDequantMatrices` mode selection.** Default cparams use LIBRARY-default matrices.
- **Phase R restoration filters** (Gaborish + EPF). `JXL_SKIP_PHASE_R=1` accounts for only ~4 of the 16-byte gap; residual upstream.

### v0.9.0l mathematical insight (preserved for follow-on bite)

libjxl's `ComputeScaledDCT(P) = M·P^T·M^T = vanilla(P^T)` for ROWS≥COLS strategies — bitstream stores TRANSPOSED layout. Verified via runtime `JXL_TRACE_AC=1 col0` dump matching first-principles prediction. Applying the transpose fix on DCT8x8 alone reduces gradient max R by 3.4× (58 → 17) but is interleaved with the 2.286× factor — both must be addressed together for byte-equality.

### Investigation log

The full investigation, including ruled-out suspects, the stage-by-stage diagnostic data, and the ranked next-bite list, lives in [`Documentation/v0.9.0-pixel-accuracy-investigation.md`](v0.9.0-pixel-accuracy-investigation.md) — that's the canonical reference for whoever picks up the next bite.

## 6. Risks and remaining work

### Risks

- **Pixel byte-equality timeline.** The v0.9.0 work has been steadily narrowing the suspect space, but the residual quantizer-scaling discrepancy doesn't have a single "drop the ×64 seed" fix. The fix is likely well-defined once the actual mechanism is identified (and may be a one-line change), but the *identification* requires either a libjxl side-by-side trace or a hand-crafted bitstream test.
- **Multi-DC-group support.** Currently throws `notImplemented` for frames spanning multiple DC groups (frames > ~2048 px). Required for full-image medical scans.
- **VarDCT encoder.** Forward path is still pending. The decoder catches up to djxl first, then the encoder builds on the same primitives.
- **Lossless JPEG-1 → JXL reversible transcoding (Phase J).** A distinguishing JPEG XL feature and a stated project requirement; not yet implemented.

### Deferred to follow-on bites

- AFV full overlay (per-AFV-kind corner placement + DC decomposition + IDCT4x4 / 4x8 dispatch). Foundation primitive `AFV.idct4x4` is in place.
- DCT128 and DCT256 strategies (extremely rare in real-world fixtures, only triggered on very large or solid-content frames at low effort).
- Metal compute backend (same `[Float]` UMA contract as `AccelerateDCT`).
- Spec-pixel hand-crafted test fixture (would localise any remaining bug definitively).
- Conformance test vector wiring (`jxl-conformance` repo).

## 10. Bottom line for management

JXLSwift is on track on two parallel deliveries:

- **Codec correctness (v0.5.0 → v0.9.0):** every cjxl distance level decodes end-to-end with hardware-accelerated IDCT on Apple Silicon. The v0.9.0 byte-equality push has narrowed the residual gap from "vague drift" to a single quantified factor (2.286×) reproducible in a 200-line standalone C++ test. Closing it requires a side-by-side libjxl trace — a bounded 1–6 hour bite, not open-ended investigation.
- **Family-API-parity (v0.9.0t–z + v0.10.0a-c):** Phases A + B + C of the JXLSwift ↔ J2KSwift alignment plan all shipped. A new shared `CompressionFamily` Swift package gives both libraries codec-agnostic generic surface today. End users can swap codecs by import only. CLI subcommands also aligned (`jxl compare`, `jxl completions`, etc.).

No external dependencies, no security exposure surface from third-party C code, full strict-concurrency Swift 6.2 — the architectural posture for DICOMkit integration is intact, **and** the family of in-house Swift compression libraries now has a shared protocol surface that scales as new codecs (HEIF, AVIF, etc.) are added.

**Recommended next checkpoints (in order):**
1. v0.9.0 byte-equality milestone — textured-fixture max byte-diff ≤ 2 across all SWEEP distances. Concrete playbook in [Documentation/NEXT-STEP-libjxl-trace.md](NEXT-STEP-libjxl-trace.md).
2. v0.10.0 family-parity polish — wire `validate` to the `jxl-conformance` test-vector harness; cross-repo push of J2KSwift's local commits.
3. v1.0.0 — production-ready VarDCT decode + start of the encoder side; package-registry release.
